# 自建监控的坑（OpenClaw 运维实录）

> 这是一份**踩坑记录**，不是教程。每条都是真实事故，附日期、现象、根因、修法。
> 环境：Windows 10/11 + Node 22 + OpenClaw + Clash 代理。部分结论与平台无关，部分只对 Windows 成立，都标注了。

---

## 坑 1：Node 原生 fetch 不读代理环境变量

**时间**：2026-11-03 实测定案

**现象**：用 `await fetch('https://api.telegram.org/...')` 的告警脚本报 `TypeError: fetch failed`（telegram 约 10.6 秒超时、交易所 API 约 125ms 秒拒），而 `curl` 请求同一 URL 却能通。

**根因**：**Node 原生 fetch（undici）不读 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量，curl 会读。**

于是产生一个极具迷惑性的对照：

| 端点 | curl（读代理 env） | Node fetch（不读） |
|---|---|---|
| 国内 API | 通 | 通（本来就是直连） |
| 被墙端点 | 通 | **必失败** |

"curl 能通"会让人以为网络没问题，实际是 curl 偷偷走了代理。

**最要命的后果**：告警脚本里如果用 fetch 发通知，**失败是静默的**。日志还很可能把原因误写成"静默时段已抑制"——你以为在盯着，其实全哑了。这种失效可以持续数周不被发现。

**三种解法**：

1. **Node 22+：`NODE_USE_ENV_PROXY=1`** —— 最省事，原生 fetch 就会读代理了（会打印一条 experimental 警告，可忽略）
2. **curl + 显式 `--proxy`** —— 最稳，但 Windows 下有引号地狱
3. **手写 HTTP CONNECT 隧道** —— 只用 `net`/`tls`/`zlib`，零依赖、无 shell 调用面，适合需要过安全扫描的场景

**判据**：新写请求前先问一句「这端点国内直连能通吗？」不能通就必须显式走代理。

## 坑 2：告警通道和被监控对象共用同一个单点

**时间**：2026-09-11 事故

**现象**：代理（本机 Clash，127.0.0.1:7897）挂掉 → 所有出站流量断 → **Telegram 告警本身也发不出去**（实测 http_code=000）。

**这是自建监控的经典死锁**：你设计了一条告警链，但它依赖的正是你要监控的那个东西。

**修法**：分级降级。

1. 首选：直发通知
2. 发送失败 → **写本地告警文件**，等外部恢复后再补报
3. 下一轮巡检读到该文件 → 补发 + 清理

关键点：**"发送失败"和"不需要发送"必须分开记录**。混在一起会让日志说谎。

## 坑 3：代理是整条链的源头单点，会连累通道

**时间**：2026-09-11

**因果链**（这条链不容易想到）：

```
代理挂 → 通道取 token 失败 → 反复重连 → 累积 unclean boot
       → 触发网关的 crash-loop breaker → 抑制全部通道自启
```

结果是 QQ 和 Telegram 全部显示 `stopped / health:not-running`，看起来像网关死了，实际网关进程活得好好的。

**诊断陷阱**：控制平面（Web UI）此时仍可用，所以如果你只用 Web UI 检查，会觉得"一切正常"。

**修法**：
- 代理侧：独立守护进程巡检端口，不通则重启代理客户端/核心
- 通道侧：独立的 supervisor 巡检通道状态，掉线则显式调用 `channels.start`
- **必须显式 start**：crash-loop breaker 抑制通道自启后，只有显式的启动指令能覆盖它（文档写得含糊，这是实测出来的）

## 坑 4：模型「半死」——HTTP 200 但不吐内容

**时间**：2026-08-16、2026-09-15 各发作约 2.5 小时

**现象**：模型 API 返回 HTTP 200，但 SSE 流不输出任何内容。请求一直挂着，直到超时。

**为什么这是最难处理的故障**：

- 对客户端来说这是「成功响应」→ **不触发 fallback**
- 对监控来说这是「有响应」→ 常规健康检查可能判为 OK
- 用户侧表现：**AI 完全失联，但日志里没有任何错误**

**修法**：
1. 健康检查必须校验**内容非空**，不能只看 HTTP 状态码
2. 健康检查请求的 `max_tokens` 不能太小 —— 推理模型会把小预算全烧在 reasoning 上，导致 content 为空，**造成误判**
3. 连续失败要**加一次确认复检**（抖动很常见，连测 3 次空可能第 4 次正常）
4. 配置 fallback 链

## 坑 5：备份模型配成了主模型本身

**时间**：2026-11-17 发现

**现象**：健康守护脚本里写着：

```js
const BACKUP_MODEL = 'deepseek/deepseek-v4-flash'; // 当前唯一可用
```

但后来主模型就改成了 flash。于是判断 `primary === BACKUP_MODEL` **恒为真** → 永远走「已是唯一模型、无法切换，请人工处理」分支 → **配置里明明有 fallback，一次都没被用上。**

**根因**：硬编码的常量随配置演进而过时，而没有任何机制会提醒你它过时了。

**修法**：备胎**从配置读**，不要硬编码：

```js
const BACKUP_MODEL = CFG.agents?.defaults?.model?.fallbacks?.[0] || null;
```

**通用教训**：**脚本里每一个硬编码的外部状态，都会在某个时刻变成谎言。** 配置、路径、端口、账号 ID —— 能读就读，读不到再降级。

## 坑 6：会话级模型覆盖会让全局切换失效

**时间**：2026-11-03

**现象**：全局切换主模型后，某个会话仍然使用出故障的模型。

**根因**：会话可以被单独钉在某个模型上（`modelOverride` / `providerOverride`）。全局 `primary` 改了也带不走它。

**修法**：切换时清理指向**故障模型**的会话覆盖，其他有意钉死的会话不动。

**附加坑**：清理代码把 sessions 记录当数组遍历，实际它是「key → 记录」的对象。按数组处理会**静默跳过所有会话**——不报错，但什么都没做。**这类静默失效比报错难查十倍。**

## 坑 7：健康探测方法本身失效（误报）

**时间**：2026-10-30

**现象**：体检脚本报「端口 18789 未监听」，但实际服务完全健康。

**根因**：用 `Get-NetTCPConnection -LocalPort 18789 -State Listen` 判断监听状态 —— 该方法在这台机器上返回 0 条（State 字段为空）。而 `netstat`、HTTP 请求、`TcpClient` 连接、`Test-NetConnection` 全部正常。

**误报统计**：日志里 11 条「网关异常」，10 条是这类误报。

**修法**：改用 .NET `TcpClient` 直连目标端口，只看 `Connected`，不依赖系统的 TCP 状态字段。

**通用教训**：**监控工具的"异常"也要被监控。** 误报的代价不只是噪音 —— 它会训练你忽略告警。

## 坑 8：告警风暴与投递状态混淆

**时间**：2026-09-15

**现象**：模型故障持续 2.5 小时，一晚发了 **7 条**相同告警。

**修法**：
- 冷却窗口：同一事件 1 小时内最多 1 条
- 夜间静默：23:00-08:00 不推（凌晨叫醒也无人处理）
- **但投递状态必须如实记录**：「静默未发」≠「发送失败」。前者是设计，后者是故障

**反面案例**：某脚本的日志把发送失败写成 `(quiet hours?)` —— 一个带问号的猜测。这个问号让故障藏了两个月。

## 坑 9：单个 turn 堵死会拖垮整个消息队列

**时间**：2026-08-22（4.8 小时）、2026-11-16（57 分钟）

**现象**：AI 完全不回消息，看起来像服务死了，实际进程正常运行。

**根因**：一次工具调用永久挂起（同步广播窗口消息等所有窗口响应）→ 占住处理队列 → 后续所有消息排队 → **心跳、定时任务全部排不进来**。

**关键数据**：2026-11-16 事故 `lane task error: durationMs=3436258` = 单个 turn 占用 **57 分钟**。

**修法**：
1. **凡是可能挂起的操作，一律加超时**
2. **长任务不塞进单个 turn**：拆成多轮，或用后台进程 + 分轮轮询
3. **同步 API 换异步**：如 Windows 窗口消息用 `PostMessage`（立即返回）而非 `SendMessage`（阻塞等响应）
4. **长流程写状态文件**：做到第几步、中间结果在哪，被中断后可续跑

## 坑 10：批量清理差点删掉个人材料

**时间**：2026-11-16

**现象**：清理脚本第一版保护规则是「保护 >1MB 的 pdf/docx/zip」。试运行清单里出现了 `成绩单-教务系统导出.pdf`，**0.3 MB** —— 按大小规则会被移入回收站。

**修法**：改成按**文件名关键词**无条件保护，不看年龄、不看大小：

```
身份证 / 户口 / 护照 / 毕业证 / 学位 / 学历 / 成绩单 / 简历 /
推荐信 / 证书 / 准考证 / 报名 / 政审 / 体检 / 缴费 / 回执
```

**通用教训**：**凡是批量清理，先看 dry-run 清单里有没有人名、证件类文件。** 不要靠大小或扩展名推断重要性 —— 一份成绩单比一个 10MB 的日志重要得多。

**配套设计**：
- 默认 dry-run，要显式 `--apply` 才执行
- 先移入回收站，满 14 天才永久删除（留反悔期）
- 报告写文件，事后可查

## 附：几条通用的监控设计原则

从上面十条里提炼出来的：

1. **活跃的监控会骗你，静默的监控不会** —— 宁可多写一行"本轮正常"，也不要只在异常时才有日志
2. **失败要分级**：不需要发 / 发送失败 / 发送成功，三者必须可区分
3. **探测方法本身会失效** —— 定期用第二种方法交叉验证
4. **硬编码的值都是定时炸弹** —— 尤其是别处会变的状态
5. **冷却与去重不是优化，是必需品** —— 否则告警会被训练性地忽略
6. **任何一个"永远为真"的条件都值得查一遍** —— 它通常意味着两边指向同一个东西
7. **降级路径要真的能走通** —— 配置了 fallback 但从不触发，等于没配

## 关于代码

本仓库的 `scripts/` 下有两个可直接参考的实现：

- `proxy-guard.mjs` —— 代理单点自愈（含"告警发不出去时改写本地文件"的降级）
- `model-health-check.mjs` —— 模型健康守护（含内容非空校验、确认复检、告警冷却、会话覆盖清理）

两者都做了参数化，个人路径/账号/端口全部走环境变量。
